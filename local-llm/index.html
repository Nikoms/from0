Local LLMs — Every Number on the Box, Explained

Beginner-friendly   LLM = Large Language Model, the kind of AI behind ChatGPT or Claude. "Qwen3.8-27B, Q4_K_M, KV q8, 100k context, 35 tok/s on a 3090." By the end of this page you will be able to compute every one of those numbers yourself — and know which ones matter.

Who this is for. You are a developer. You have heard you can run ChatGPT-like models on your own laptop or a graphics card, and you have opened one Reddit thread and closed it again because every sentence looked like UD-IQ3_XXS with KV q4 gets 20 t/s at 70k ctx on a 4070 Ti Super. This page decodes that sentence, one number at a time, with sliders you can drag. It starts from zero: §0 gives every word in one line, then each section builds on the previous one. No maths beyond multiplication and division. If you want to know what happens inside the model, that's the MicroGPT course. This page is about what happens around it: files, memory, speed, money.

1. A model is a big file of numbers

A language model is not code. It is a huge table of numbers called parameters (or weights). A parameter is one number that training adjusted: in the school formula y = 0.7·x + 2.1, 0.7 and 2.1 are the two parameters — change them and the line moves. A model is that formula scaled up: it takes the tokens so far as input, multiplies and adds them with its parameters, and outputs the probability of the next token. When you read "Qwen3.8-27B", the 27B means 27 billion parameters — a spreadsheet with 27,000,000,000 cells, none of which a human wrote by hand. The MicroGPT you built in Java had a few thousand. Same recipe, one million times bigger. "Qwen" is Alibaba's family of open models — the one that runs on your machine; the same page applies to Llama (Meta), Mistral, GLM, MiniMax, DeepSeek…

Every one of those numbers has to be stored somewhere. How many bytes each number takes is called its precision. That's the first thing that decides whether a model fits on your machine. The names say it: BF16 = brain float, 16 bits; FP8 = floating point, 8 bits; Q4 = quantized (rounded) to 4 bits. Divide bits by 8 to get bytes.

2. Dense vs Mixture of Experts — why a bigger model can be faster

Remember the one formula: speed depends on how many bytes the model must read per token. A dense model uses every parameter for every token. Qwen3.8-27B at Q4 reads all 16 GB, for every single word it writes.

A Mixture of Experts (MoE) model is built differently. Its layers contain many small "experts", and a tiny router (a small learned layer inside the model) picks two or four of them per token. Qwen3.6-35B-A3B has 35B parameters on disk but only 3B are active for any given token. It reads about 1/9th of the bytes a 27B dense model reads. In practice that buys 3–5× (not 9×): with so few bytes per token, other costs — attention, the KV cache, launching the GPU work — stop being negligible.

Real-life analogy. A dense model is a hospital where every doctor examines every patient. An MoE is a hospital with a receptionist who sends you to two specialists. Much faster per patient — but you still need the whole building (all 35B must sit in memory), and two specialists know less than the whole staff put together.

3. Quantization — smaller numbers, slightly worse answers

Quantization means storing each parameter with fewer bits. Think of prices: €12.47 (full precision) → €12.50 (Q8) → €12 (Q4) → €10 (Q2). The shop still works with rounded prices; it just gets a little less exact with every step.

What you gain

Smaller file → fits on smaller cards → fewer bytes per token → faster. Q4 is 3.3× smaller and 3.3× faster than BF16.

What you lose

Accuracy. Q8 ≈ nothing. Q4 ≈ a point or two on benchmarks. Q3 ≈ visible. Q2 ≈ a different, dumber model wearing the same name.

The benchmark trap. Every score you read on a model card ("SWE-bench Pro 61.7") was measured at full precision. The Q4 you download is a bit below that; the Q2 that "runs on my 16 GB card" is well below it. When someone says "27B beats Opus 4.6 on my laptop", ask what quant.
The letters after the number. K_S / K_M / K_L / K_XL = small/medium/large/extra-large variants of the same bit-width (more letters = more layers kept precise, slightly bigger file). IQ = a different, denser packing format — smaller for the same quality, slower to decode. Any quant (K or IQ) can be built "with imatrix" (i1-): the packer measured which weights matter and protected those. _0 / _1 = older simple recipes. Rule of thumb: Q4_K_M or UD-Q4_K_XL unless you have a reason.

One more thing can be quantized: the KV cache (§5). "KV q8" is nearly free. "KV q4" saves memory but hurts the model's memory of long conversations. Use q8.

4. Tokens and the context window

Models don't read letters or words; they read tokens — chunks of text from a fixed vocabulary (the walkthrough bonus section explains why). Rules of thumb for English: 1 token ≈ 4 characters ≈ ¾ of a word. Code is denser: 1 token ≈ 3 characters. French ≈ 3.5.

The context window is the maximum number of tokens the model can look at in one go: your instructions + the files you pasted + the conversation so far + the model's own thinking (§8) + its answer. Qwen3.8-27B advertises 262,144 tokens ("262k") — roughly 200,000 words, two novels. Once the window is full, the oldest part falls off (or the tool refuses).

Demo 2 — How many tokens is that?

Why coding agents eat context. A coding agent (Claude Code, OpenCode…) doesn't send one question. It sends the system prompt, the tool descriptions, every file it opened, every command output, and the whole conversation — every turn. A normal session sits at 30–100k tokens. That is why "can it do 100k context?" is the real question, not "can it run?".

5. The KV cache — the memory that grows as you talk

In the attention chapter, every token computed a Key ("what am I about") and a Value ("what I contribute") vector so later tokens could look back at it. When a model generates text, it would be silly to recompute the Keys and Values of the whole conversation for every new token. So it stores them: that store is the KV cache.

It lives in the same GPU memory as the weights, and it grows with every token in the window:

KV cache  =  tokens in context  ×  bytes per token

How many bytes per token depends on the architecture: number of layers × 2 (K and V) × how many attention heads keep a cache × head size × bytes per number. You don't need to compute it; you need to know it varies a lot:

6. Two speeds: prefill and decode

The one formula. Everything you have read so far collapses into one line:
tokens per second  ≈  memory bandwidth (GB/s)  ÷  gigabytes the model must read to produce one token
The rest of this section shows why, and §7 shows how to read that off a graphics-card spec sheet.

Generation happens in two phases, and they are limited by two different parts of your hardware.

Prefill — reading your prompt

All the prompt tokens are processed at once, in parallel. This is pure arithmetic: limited by compute (TFLOPS). Measured in tokens/s of input. Determines the time to first token (TTFT).

Decode — writing the answer

One token at a time. For every token, the GPU must read all the active weights from memory once. Limited by memory bandwidth (GB/s). Measured in tokens/s of output. This is "the tok/s" people quote.

decode tok/s  ≈  bandwidth (GB/s) ÷ bytes read per token (GB)  ×  ~0.65 (real-world efficiency)

Worked example, Qwen3.8-27B at Q4 (16 GB read per token):

Try this. Pick the MacBook Air and a 100k prompt. Prefill at ~40 tok/s means 40 minutes before the first word. Two tricks that bend the formula.
Speculative decoding / MTP (multi-token prediction). A tiny helper guesses the next 3 tokens; the big model verifies all 3 in one memory pass. When guesses are right (code: ~75 % of the time) you get 1.5–2.5× decode for free. Qwen3.8 ships this "MTP head" built in: an RTX 5090 goes from ~70 to ~148 tok/s on code with it. It needs good kernels — on Apple Metal it currently makes things slower.
Batching. On one data-center GPU serving Qwen3.8-27B (vLLM), one user gets 226 tok/s; 16 users at once get 2,281 tok/s in total. The card was mostly waiting on memory; serving many people at once fills the gap. This is why renting a model per token is so cheap: you share the card.

7. The three numbers of a graphics card

Marketing sheets list twenty specs. For running models, three matter, in this order:

  1. Memory size (GB of VRAM — video RAM, the graphics card's own memory — or "unified memory" on Macs / the DGX Spark) — decides what fits: weights + KV cache + ~1.5 GB overhead (§1, §5).
  2. Memory bandwidth (GB/s) — decides decode speed (§6). Not the number of "cores", not the clock: bandwidth.
  3. Compute (TFLOPS) — decides prefill speed, i.e. how long you wait on big prompts.

Unified memory vs a graphics card

On a Mac or a DGX Spark, CPU and GPU share one pool ("unified memory"): a 32 GB Air can give ~25 GB to the model. On a PC, the model must fit in the graphics card's own memory (VRAM); what doesn't fit is "offloaded" to normal RAM and runs 10–20× slower over the PCIe cable. A 16 GB card running a 20 GB model is not "a bit slower" — it falls off a cliff.

8. Thinking, reasoning effort, sampling

Modern models can think before answering: they write a hidden scratchpad ("let me check… actually…") and only then the answer. It makes them smarter on hard problems and slower on everything. Those thinking tokens count against your context and your patience: one YouTuber let Qwen3.8-27B think for 33 minutes on a logic puzzle.

  • Reasoning effort (low / medium / high): how long it is allowed to think. For coding agents, low is usually right — the agent iterates anyway. Gotcha: in Ollama, Qwen3.8's default is the highest effort. Set it explicitly.
  • Temperature: randomness. 0 = always the most likely token (deterministic, repetitive). 0.6–0.7 = normal. 1+ = creative / unstable. Use the model card's recommended value.
  • top_k: only consider the K most likely next tokens. top_p: only the smallest set of tokens whose probabilities add up to p (e.g. 0.95). Both are guardrails on temperature. Again: model card values.
  • System prompt: the instructions the tool sends before your message. In agents it is thousands of tokens — part of your context budget.

12. Play with the real thing (MacBook Air edition)

Everything above can be checked in ten minutes on the Air with Ollama installed.

# 1. See what's on disk and how big (§1)
ollama list

# 2. Watch the memory split — weights + KV cache + overhead (§5)
ollama run qwen3.6:35b "hi" > /dev/null; ollama ps

# 3. Measure decode and prefill yourself (§6) — 'eval rate' = decode, 'prompt eval rate' = prefill
ollama run qwen3.6:35b --verbose "Write a Python function that parses ISO-8601 durations."
ollama run qwen3.8:27b-mlx --verbose "Write a Python function that parses ISO-8601 durations."

# 4. Same request through the API, with reasoning effort pinned to low (§8)
curl -s localhost:11434/api/generate -d '{
  "model": "qwen3.8:27b-mlx", "think": "low", "stream": false,
  "prompt": "Explain the KV cache in two sentences."
}' | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["response"]); print("decode tok/s:", round(d["eval_count"]/d["eval_duration"]*1e9,1))'

# 5. Check how much memory the GPU is allowed to take (Apple unified memory, §7)
sysctl iogpu.wired_limit_mb
What you should see. Step 3: the 35B-A3B (MoE) writes ~3× faster than the 27B (dense) even though its file is bigger — §2 in real life. Step 4: run it twice, once with "think": "low" and once without the field: the second one thinks for ages, because the default effort is the highest. Feed a 10,000-word text as the prompt and watch prompt eval rate — that's the prefill wall from §6.

13. Cheat sheet

Parameters / weights

The numbers that make up the model. "27B" = 27 billion.

Dense

Every parameter is used for every token. Smart per GB, slow per token.

MoE, "A3B"

MoE = Mixture of Experts, A3B = 3B Active; only the "active" part is read per token. Fast, needs the whole thing in memory.

BF16 / FP8 / Q8 / Q4 / Q2

Bits per parameter (BF = brain float, FP = floating point, Q = quantized). Bytes: 2 / 1 / 1 / 0.6 / 0.35. Smaller = faster and dumber.

Quantization

Storing weights with fewer bits. Q4_K_M is the default choice.

GGUF

"GPT-Generated Unified Format" — file format for llama.cpp / Ollama / LM Studio.

Token

Chunk of text, ~4 characters. Models count everything in tokens.

Context window

Max tokens visible at once (262k for Qwen3.8). Costs memory via the KV cache.

KV cache

KV = Key/Value. Stored attention Keys/Values for every token in context. Grows with context; ~35 KB/token on Qwen3.8-27B at q8.

Prefill

Reading the prompt. Compute-bound. Sets time-to-first-token.

Decode

Writing the answer, one token at a time. Bandwidth-bound. "tok/s".

tok/s

Tokens per second. 5 = painful, 30 = fine for an agent, 100 = pleasant chat.

TTFT

Time To First Token = prompt tokens ÷ prefill speed.

VRAM / unified memory

Memory the model must fit in. Weights + KV + ~1.5 GB.

Bandwidth (GB/s)

How fast memory can be read. The number that sets decode speed.

Offload

Putting part of the model in slow CPU RAM. 10–20× slower for that part.

MTP / speculative decoding

MTP = Multi-Token Prediction. Guess-then-verify trick; 1.5–2.5× decode when it works (CUDA yes, Metal not yet).

Batching / concurrency

Serving many requests at once. Why cloud tokens are cheap.

Thinking / reasoning effort

Hidden scratchpad before the answer. low/medium/high. Costs tokens and time.

Temperature, top_p

Randomness knobs. Use the model card's values.

CUDA / ROCm / Metal

NVIDIA / AMD / Apple GPU software layers. CUDA is supported first, everywhere.

llama.cpp, Ollama, MLX, vLLM

Engines. Ollama = easy; MLX = fast on Macs; vLLM = servers.

SWE-bench Pro / Terminal-Bench

Coding-agent benchmarks. Vendor-reported, full precision.

$/M tokens

Cloud price per million tokens, input and output priced separately; cached input ~10 %.

LLM / model

Large Language Model: billions of learned numbers that predict the next token. Files you download, not programs.

Qwen, Llama, GLM, MiniMax…

Families of open models you can download: Qwen (Alibaba), Llama (Meta), GLM (Zhipu), MiniMax, DeepSeek, Kimi (Moonshot). Claude / GPT are closed: cloud only.

GPU / graphics card

Graphics Processing Unit: the chip built for millions of parallel multiplications — exactly what a model needs. Its own memory is the VRAM.

NVIDIA RTX, AMD Radeon, Apple Silicon

The three GPU makers. RTX / RTX PRO = NVIDIA's consumer / workstation lines; Radeon = AMD; Apple Silicon = the M-series chips in Macs.

DGX Spark / ASUS GX10

NVIDIA's small desktop AI computer (128 GB unified memory, slow-ish bandwidth). GX10 is ASUS's version of the same design.

Layer

One of the ~30–80 stacked processing stages inside a model; each token passes through all of them.

Kernel

A small program that runs one operation on the GPU. "Better kernels" = the same maths done faster.

OpenRouter

A marketplace that sells access to many cloud-hosted models per token through one API.

PCIe / PSU

PCIe = the slot connecting a graphics card to the PC (slow compared to VRAM). PSU = power supply unit.

MIT / Apache 2.0 (license)

Open-source licenses on the model files: use, modify, sell — allowed. "Open model" = weights you can download; Claude/GPT are not.

Lossy / lossless

Whether the compression changed the answers. Q8 ≈ lossless; Q2 = lossy: it runs, but it is measurably dumber.

TFLOPS / compute

Trillions of arithmetic operations per second. Sets prefill speed (reading your prompt).

Hybrid attention / Gated DeltaNet

Only some layers keep a per-token KV cache; the rest keep a fixed-size summary. Makes long context cheap (Qwen3.5+).

Coding agent

A tool (Claude Code, OpenCode…) that lets the model read files, run commands and iterate. Re-sends the whole context every turn.

Where the numbers come from. Measurements on a MacBook Air M4 32 GB (June–Aug 2026), public benchmarks of the RTX 3090 / 5090 / R9700 / DGX Spark by their owners, Qwen's model cards, OpenRouter and Belgian retailer prices on 16 Aug 2026. Everything marked "~" or "est." is the formula, not a measurement. Prices and speeds move; the formulas don't.
